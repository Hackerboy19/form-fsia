# Role and Permission Matrix

## Roles that exist (`cms/backend/lib/rbac.php`)

| Role | Meaning |
|---|---|
| Owner | Everything, including giving roles |
| Admin | Everything except giving roles |
| Editor | Edit content; view the tools |
| Viewer | View only |

**Current setup: single admin.** `roles_enabled` is not set in `config.php`, so every signed-in admin has Owner rights, and the Users & Roles screen is hidden. `users.php` answers only `?action=me`; setup and role changes return 409. The matrix below applies only once `'roles_enabled' => true` is added.

How roles behave:
- Roles stay off until an owner turns them on. Until then every signed-in user has Owner rights, as before.
- The `config.php` admin token always acts as Owner.
- A user added later with `set-password.php` starts as a Viewer.

## Escalation and other checks (all passed)

- An editor cannot make itself an owner (403).
- The last owner cannot be demoted (409).
- An owner can step down once another owner exists, and then loses Users & Roles.
- A token edited to carry another user's name is refused (401).
- Every refusal is written to the Activity Log with user, role and IP.

## The starindia admin (separate system)

`starindia.fsia.in/admin` has its own users, roles and permissions (`/api/auth/users`, `/roles`, `/permissions`; checks such as `profiles.view`). Its code is not in this repository, so its matrix was **not tested** (BLOCKED). The CMS only links to it; the deep link script runs inside it under whoever is signed in there, and never saves.

## Not covered

- **The old admin panel `/fsiaadmm21/` and `starindia.fsia.in`**: their code is not in the repo, and they have their own logins. These roles do not apply to them.
- **Profile owners (public users)**: they have no login. Their identity is the OTP at registration.
