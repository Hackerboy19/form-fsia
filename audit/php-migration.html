TL;DR

  • Reality

    PHP itself isn't the security problem. The site runs PHP 8.3, which gets security fixes until the end of 2027. The risk comes from how the site is built: no framework, 73 copied files, hand-written SQL, secrets in code, public include files, no CSRF tokens or security headers, no tests, and most code outside git.

  • Recommendation

    Move to Next.js (TypeScript) behind Cloudflare, keeping the existing MySQL database. CSRF protection, output escaping, typed validation, static pages and image optimisation become defaults. This also fixes most of the speed and sitemap problems.

  • Approach

    Migrate route by route, with no big-bang switchover. Cloudflare sits in front and sends one URL group at a time to the new app while PHP keeps serving the rest. Each step can be rolled back by changing a route.

  • First

    Phase 0 hardens the current PHP site: the Bharat Couture 404, the OTP endpoint, headers and caching. Those can't wait 20 weeks.

  • SEO

    Every existing URL keeps working, either served directly or 301'd. A full crawl comparison gates each cutover.

Approach

Route-by-route migration

                  ┌───────────────────── Cloudflare ─────────────────────┐
 visitor ───────► │  route table (changed one URL group at a time)       │
                  └──────────────┬───────────────────────┬───────────────┘
                                 │ migrated routes       │ everything else
                                 ▼                       ▼
                        Next.js app (new)        PHP on Plesk (old)
                                 │                       │
                                 └──────► MySQL ◄────────┘   (shared during migration)
  • Both apps read and write the same database, so the back office and reports don't change while pages move.
  • Each URL group moves only after its parity crawl passes: same status, canonical, title, H1, schema type and indexability.
  • Rollback means pointing the route back to PHP, which takes seconds.
